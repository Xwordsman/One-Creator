# One-Creator 项目文档

> 项目暂定名：**One-Creator**。文档基线建立于 **2026-10-16**。
> 当前已有 `v0.1.0-alpha.1` 实现切片；功能实现与验收状态以 [开发进度](progress.md) 为准。

One-Creator 计划成为面向个人创作者的开源自媒体工作台，围绕多账号、多种创作风格，串联选题、素材、AI 创作、平台适配、发布计划和复盘。当前方案以 **Web 工作台 + Docker 自部署**为方向。

## 建议阅读顺序

- 了解产品：产品定位 → 开源调研 → 功能需求。
- 开始开发：开发进度 → 对应需求 → 用户流程 → 架构与数据模型 → 验收计划。
- 核对成果：开发进度中的证据 → 对应验收标准 → 完成记录。
- 调整计划：决策记录 → 需求与路线图 → 进度表 → 变更记录。

## 文档维护约定

### 1. 每类信息有唯一维护位置

| 信息 | 维护位置 |
| --- | --- |
| 功能定义、功能 ID、验收标准 | `requirements.md` |
| 优先级、目标阶段、当前状态、实现证据 | `progress.md` |
| 阶段目标、开发顺序、阶段出口 | `roadmap.md` |
| 方案取舍、尚未验证的假设 | `decisions.md` |
| 外部项目和平台能力的来源 | `research.md` |
| 变更经过 | `changelog.md` |

其余文档通过 ID 和链接引用，避免在多处维护不同的完成状态。

### 2. 使用固定 ID

- 需求：`ACC-01`、`CRE-05`、`PUB-02` 等；质量要求使用 `NFR-*`。
- 决策：`DEC-*`；待验证实验：`POC-*`；验收场景：`VAL-*`。
- 同一个 ID 贯穿文档、后续任务、代码变更和验收记录。
- ID 分配后不复用。拆分或取消需求时保留原条目，并记录后继 ID 或取消原因。
- 新增需求应同时加入需求文档和进度表；不能只在讨论或路线图中留下名称。

### 3. 区分规划、实现和验证

需求写入文档、界面有按钮、外部项目有此功能，都不表示 One-Creator 已完成对应能力。

只有实现了需求、通过相应验收、补齐证据，才可在进度表中标记 `DONE`。模拟数据测试、真实平台验证、用户手工回填应明确注明。

### 4. 每次开发同步更新

1. 开始前认领需求 ID，检查定义、依赖和待确认项，将状态更新为 `DOING`。
2. 有可验收成果后记录代码路径、变更引用和检查结果，进入 `VERIFY`。
3. 验收通过后标记 `DONE`，补充完成日期和已知限制。
4. 发生范围、架构或验收口径调整时，同步更新决策及变更记录。
5. 有部分实现但尚未通过完整验收时保留 `DOING` 或 `VERIFY`，明确剩余项。

状态定义、记录模板见 [开发进度](progress.md)。

## 当前基线的解读

- 用户已明确：自用优先、希望开源、多平台多账号、需要 AI 辅助、文档要支持长期核对开发进度。
- 首个切片已选择 React / Vite、Fastify、PostgreSQL / PGlite、npm workspaces 和 MIT 许可证；选型依据记录在 `decisions.md`。
- 全量需求用于保留产品全景；阶段划分属于初始建议，可以调整。
- 仓库说明和平台政策具有时效性。接入前按具体版本及实际账号重新核验，记录到对应 `POC`。

继续开发时，优先查看 [开发进度](progress.md) 的剩余范围，以及 [开发指南](development.md)。
